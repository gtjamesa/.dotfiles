Fix a set of triaged issues, each on its own branch and PR, so the user can merge or hold each one separately. Each issue's **agent brief** (the `## Agent Brief` comment from `/triage`) is its spec.

Tracker operations (read, claim, comment, label) follow `docs/agents/issue-tracker.md`; role names map to labels via `docs/agents/triage-labels.md`. If either is missing, tell the user to run `/setup-matt-pocock-skills` and stop.

Communicate through **context pointers**: issue numbers, branch names, PR numbers, file paths. Subagents read the issue themselves; copied text goes stale and bloats their context.

## 1. Frontier

Candidates are the issue numbers in `$ARGUMENTS` (`#1500`, `1500`, any separators). With no arguments, list open issues with the `ready-for-agent` role.

Fetch each candidate's state, assignees, labels, dependencies and comments. The **frontier** is every candidate that is open, unassigned, labelled `ready-for-agent`, has no open blocker, and has an agent brief. Record every other candidate with its reason; they go in the final table.

## 2. Lanes

Read each brief's **Key interfaces**. Issues naming the same type, class, endpoint group or subsystem share a **lane**; when overlap is unclear, share the lane. Each lane runs one issue at a time; lanes run in parallel. Order within a lane: priority-labelled issues first, then by number.

Give each issue a **slot**: a distinct integer from 1, used wherever the repo's worktree docs need a per-checkout value (test DB token, port).

## 3. Implement

For the head of each lane, in the order of step 2:

1. **Claim late.** Re-fetch the assignees immediately before claiming. If someone else holds it, record it as skipped and move to the lane's next issue. Otherwise claim it.
2. Spawn a **background implementer** subagent. Point it at [`IMPLEMENTER.md`](IMPLEMENTER.md) in this skill's base directory (absolute path) and give it: issue number, branch `<type>/<n>-<slug>` (`fix` for a bug, `feat` for an enhancement), worktree name `<n>-<slug>`, slot, and the PR number of the lane's previous issue, if any.

## 4. Review

When an implementer reports a PR, spawn a fresh subagent to run the Skill tool with `code-review` in that worktree, with fixed point `origin/main`. Send the findings to the implementer (SendMessage). One round; the points it declines are the issue's **open review points**.

Then start the lane's next issue at step 3.

## 5. Stuck

An implementer that reports **stuck** has hit something only a human can resolve. On that issue:

1. Comment, starting with `> *This was generated by AI during implementation.*`, followed by the implementer's stuck report.
2. Swap the `ready-for-agent` role for `ready-for-human`, so later runs leave it out of the frontier and it surfaces for a human.
3. Unassign yourself.

Then start the lane's next issue at step 3.

## 6. Finish

Done when every frontier issue has a PR through review, or is stuck.

1. Remove the worktrees of every PR opened and every stuck issue; their branches stay pushed.
2. Send a push notification (PushNotification tool) summarising the run.
3. Report a table: issue, PR link, test status, open review points. Below it, one line per skipped or stuck issue with its reason.
